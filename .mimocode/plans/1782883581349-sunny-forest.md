# Payment Success/Failure Flow Analysis

## Current Flow Summary

### Backend (`PaymentController::callback`)

| Scenario | Payment Status | Order Status | Redirect |
|----------|---------------|--------------|----------|
| Verify success | `paid` | `confirmed` | `/confirm` |
| `InvalidPaymentException` | `failed` | `pending` (payment_status: `failed`) | `/checkout` |
| Generic exception | unchanged | unchanged | `/checkout` |
| No pending payment found | — | — | `/checkout` or `/confirm` (if already paid) |

### Scheduled Command (`orders:cancel-unpaid`)
- Runs every minute
- Cancels orders where `status=pending`, `payment_status=pending`, older than 20 min
- **Does NOT cancel orders with `payment_status=failed`**

### Frontend
- **ConfirmPage**: Generic success page with **random** tracking code (not real data)
- **CheckoutPage**: Returns to checkout form with **no error message** about failure

---

## Issues Found

### 1. ConfirmPage shows fake data
- `ZT-{Math.floor(100000+Math.random()*900000)}` — random number, not real order
- No API call to verify actual payment status
- Static "سفارش با موفقیت ثبت شد" message regardless of reality

### 2. No failure feedback on checkout return
- Backend redirects to `/checkout` on failure but passes no query params
- User sees checkout form again with no toast/error explaining what happened
- Confusing UX — user doesn't know payment failed or why

### 3. Failed orders never cancelled
- `CancelUnpaidOrders` only cancels `payment_status=pending`
- Orders with `payment_status=failed` stay forever as `status=pending`
- These are zombie orders that will never be paid

### 4. No user notification on cancellation
- Cancelled orders are silently updated in DB
- User has no way to know their abandoned order was cancelled

---

## Plan

### A. Backend: Pass failure info via query param

**File:** `app/Http/Controllers/Api/PaymentController.php`

In the `callback` method, when payment fails, add a query param:

```php
// On failure:
return redirect($frontendUrl.'/checkout?payment=failed');

// On exception:
return redirect($frontendUrl.'/checkout?payment=error');
```

### B. Frontend: Show failure toast on checkout

**File:** `src/app/pages/CheckoutPage.tsx`

On mount, check for `payment=failed` query param and show toast:

```tsx
useEffect(() => {
  const params = new URLSearchParams(window.location.search);
  if (params.get('payment') === 'failed') {
    toast.error("پرداخت ناموفق بود. لطفاً مجدداً تلاش کنید.");
    window.history.replaceState({}, '', '/checkout');
  } else if (params.get('payment') === 'error') {
    toast.error("خطا در تایید پرداخت. لطفاً با پشتیبانی تماس بگیرید.");
    window.history.replaceState({}, '', '/checkout');
  }
}, []);
```

### C. Frontend: ConfirmPage fetches real order data

**File:** `src/app/pages/ConfirmPage.tsx`

Replace random tracking code with real data from URL params or API:

- Backend already passes `orderId` in callback URL — the frontend can use this
- Add a query param `?orderId=123` to the confirm redirect
- ConfirmPage calls `api.payment.status(orderId)` to get real data
- Display real order number and tracking code

**File:** `app/Http/Controllers/Api/PaymentController.php`

Update success redirect:
```php
return redirect($frontendUrl.'/confirm?order_id='.$order->id);
```

### D. Backend: Cancel failed-payment orders too

**File:** `app/Console/Commands/CancelUnpaidOrders.php`

Extend the query to also cancel orders with `payment_status=failed`:

```php
$cancelled = Order::where('status', 'pending')
    ->where(function ($q) {
        $q->where('payment_status', 'pending')
          ->orWhere('payment_status', 'failed');
    })
    ->where('created_at', '<', now()->subMinutes(20))
    ->update([
        'status' => 'cancelled',
        'cancel_reason' => 'عدم پرداخت ظرف ۲۰ دقیقه',
    ]);
```
