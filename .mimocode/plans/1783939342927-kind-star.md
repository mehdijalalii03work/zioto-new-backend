# ZIOTO Backend - Comprehensive Production Code Review

**Date**: 2026-07-13
**Reviewer**: Principal Software Architect / Staff Laravel Engineer
**Stack**: Laravel 13, Filament v5, Spatie Permission, Spatie Media Library, Shetabit Multipay, nwidart/laravel-modules

---

## Executive Summary

This is an Iranian precious metals e-commerce platform with OTP authentication, real-time price board, Hesabfa accounting integration, and multi-gateway payment. The architecture has a solid foundation but has **critical security vulnerabilities, missing transaction safety, no test coverage, and multiple production-breaking issues** that must be addressed before deployment.

**Overall Assessment: NOT production-ready.** The codebase requires significant hardening before it can reliably handle real users and real money.

## CRITICAL Issues (Must Fix Before Any Deployment)

### C1. SQL Injection in CartController
- **Severity**: CRITICAL | **Category**: Security
- **File**: `app/Http/Controllers/Api/CartController.php:50`
- **Problem**: `DB::raw("GREATEST(quantity + {$quantity}, 1)")` interpolates `$quantity` directly from `request()->input('quantity', 1)` without any sanitization or type casting.
- **Why it matters**: Any authenticated user can inject arbitrary SQL. This is a textbook SQL injection vulnerability. An attacker could read the database, escalate privileges, or destroy data.
- **Fix**: Use `DB::raw("GREATEST(quantity + ?, 1)")` with parameter binding, or better yet: `$cart->quantity = max(1, $cart->quantity + (int) $quantity); $cart->save();`
- **Laravel Best Practice**: "No raw SQL with user input - use Eloquent or query builder"
- **Estimated Impact**: Full database compromise

### C2. .env File Written from Admin Panel Without Sanitization
- **Severity**: CRITICAL | **Category**: Security
- **File**: `app/Filament/Pages/ManageSettings.php:286`
- **Problem**: `file_put_contents($envPath, $envContent)` writes directly to `.env`. The `setEnvValue()` method does not quote values or escape special characters. A value like `foo\nAPP_KEY=hacked` would inject a new env variable.
- **Why it matters**: An admin (or anyone who compromises an admin session) can inject arbitrary environment variables including `APP_KEY`, effectively taking over the entire application. In shared hosting, the .env write could also fail silently.
- **Fix**: Store Hesabfa config in the `settings` table (like tax settings) instead of `.env`. If `.env` writes are unavoidable, wrap values in quotes and escape embedded quotes/newlines. Better yet: use `config:cache` and store secrets in the database or vault.
- **Laravel Best Practice**: "env() only inside config files" / "Never commit .env, use config() for secrets"

### C3. API Tokens Stored in Plaintext in Database
- **Severity**: CRITICAL | **Category**: Security
- **File**: `app/Http/Middleware/AuthenticateApiToken.php:20`, `app/Models/User.php`
- **Problem**: `User::where('api_token', $token)->first()` stores the full 64-character token in the `users.api_token` column. If the database is compromised (SQL injection, backup leak, unauthorized access), every user's session token is immediately usable.
- **Why it matters**: A database breach (which is more common than you think) instantly gives the attacker access to every authenticated user's account. Token comparison is also not timing-safe.
- **Fix**: Store `hash('sha256', $token)` in the database. On lookup: `User::where('api_token_hash', hash('sha256', $token))->first()`. Use `hash_equals()` for comparison.
- **Laravel Best Practice**: "Use `encrypted` cast for sensitive DB fields"

### C4. No Transaction Safety on Order Creation
- **Severity**: CRITICAL | **Category**: Data Integrity
- **File**: `app/Http/Controllers/Api/OrderSubmitController.php:115-138`
- **Problem**: Order creation performs 4 separate database operations (Order::create, multiple items()->create, OrderShipping::create) outside any transaction. If the process crashes between creating the order and creating order items, you get an order with no items.
- **Why it matters**: Under load or server restarts, orphaned orders with no items will accumulate. Payment will be initiated for an order with 0 items. The Hesabfa observer will attempt to sync an incomplete order.
- **Fix**: Wrap the entire store method in `DB::transaction(function () { ... })`. This is non-negotiable for financial operations.
- **Laravel Best Practice**: "dispatchAfterCommit usage" / transaction safety for multi-table writes

### C5. Payment Callback Not Protected Against Race Conditions
- **Severity**: CRITICAL | **Category**: Data Integrity / Financial
- **File**: `app/Http/Controllers/Api/PaymentController.php:148-218`
- **Problem**: The callback handler finds the pending payment, verifies it, then updates payment + order. If the gateway sends the callback twice (which happens in practice), or if the user double-clicks, the verification may succeed twice, or the order status may be set to 'confirmed' while the first callback is still processing.
- **Why it matters**: Double-crediting, duplicate order confirmations, inconsistent payment records.
- **Fix**: Use `DB::transaction()` with a lock on the payment record: `Payment::where('id', $payment->id)->lockForUpdate()`. Check status inside the transaction. Consider using `ShouldBeUnique` on a job that processes the callback.

### C6. SSL Verification Disabled on External API Calls
- **Severity**: CRITICAL | **Category**: Security
- **File**: `app/Services/PriceBoardService.php:30` (`->withoutVerifying()`)
- **Problem**: SSL certificate verification is disabled for the price board API call. Also likely in payment drivers (Kamanlend, Smartis).
- **Why it matters**: Man-in-the-middle attacks can inject fake price data, manipulate payment amounts, or steal API credentials. For a financial application, this is catastrophic.
- **Fix**: Remove `withoutVerifying()`. If there are certificate issues, fix the server's certificate chain. Use `Http::withOptions(['verify' => true])`.
- **Laravel Best Practice**: "Explicit timeout and connectTimeout on every request"

### C7. No Rate Limiting on Order Creation
- **Severity**: CRITICAL | **Category**: Security / Abuse
- **File**: `routes/api.php:59` - `POST /api/orders` has no throttle middleware
- **Problem**: The order creation endpoint has no rate limiting. An authenticated user can create unlimited orders.
- **Why it matters**: Race condition exploitation, database flooding, potential for stock manipulation (items get reserved on order creation via StockReservationObserver).
- **Fix**: Add `throttle:10,1` or similar to the order creation route.

## HIGH Issues (Fix Before Production)

### H1. API Token Not Invalidated on Logout
- **Severity**: HIGH | **Category**: Security
- **File**: `app/Http/Controllers/Auth/OtpController.php:176-186`
- **Problem**: `Auth::logout()` destroys the session but does NOT clear the `api_token` column. The bearer token remains valid indefinitely.
- **Why it matters**: A stolen token can never be revoked. If a user logs out on one device, the token stolen from that device still works.
- **Fix**: Add `$user->update(['api_token' => null]);` before session invalidation. Also add token expiry mechanism.

### H2. No Token Expiry
- **Severity**: HIGH | **Category**: Security
- **File**: `app/Http/Middleware/AuthenticateApiToken.php`
- **Problem**: API tokens generated via `Str::random(64)` never expire. They are valid forever until the user logs in again (which generates a new token, but the old one is not invalidated).
- **Why it matters**: Stolen tokens provide permanent access. No way to force re-authentication for security events.
- **Fix**: Add a `token_created_at` column. In middleware, check if `now()->diffInHours($user->token_created_at) > 72` and reject if expired.

### H3. Mass Assignment Risk in Order Creation
- **Severity**: HIGH | **Category**: Security
- **File**: `app/Http/Controllers/Api/OrderSubmitController.php:115-125`
- **Problem**: The Order model has `'hesabfa_contact_code', 'hesabfa_invoice_number', 'hesabfa_invoice_reference', 'hesabfa_synced_at'` in `$fillable`. A malicious user could pass these fields in the request and pre-set them to forge Hesabfa sync status.
- **Why it matters**: An attacker could mark an order as "already synced to Hesabfa" to prevent accounting integration, or set a fake invoice reference.
- **Fix**: Remove Hesabfa fields from `$fillable` on Order model. Use `$guarded` or explicitly set these fields only in the observer.

### H4. Hesabfa Webhook Has No Authentication When Secret Is Empty
- **Severity**: HIGH | **Category**: Security
- **File**: `app/Http/Controllers/Api/HesabfaWebhookController.php:24-35`
- **Problem**: `if ($secret) { ... }` means if `HESABFA_WEBHOOK_SECRET` is not set, anyone can POST to `/api/hesabfa/webhook` and trigger stock/price changes.
- **Why it matters**: An attacker can manipulate product stock and prices by sending fake webhook payloads.
- **Fix**: Reject requests when webhook secret is not configured, OR require the secret to always be set. Log a warning on startup if not configured.

### H5. Product Price Not Recalculated When Observer Updates Stock
- **Severity**: HIGH | **Category**: Business Logic
- **File**: `app/Services/StockSyncService.php:54-58`
- **Problem**: `StockSyncService::syncAllStock()` updates `stock_quantity` but does NOT recalculate dynamic prices for products with `price_type = 'dynamic'`. Price changes from the price board are handled separately, but stock updates that should trigger price recalculation don't.
- **Why it matters**: Dynamic prices may be stale after stock sync.
- **Fix**: After stock update, if product has `price_type = 'dynamic'`, recalculate and save price.

### H6. Race Condition in Stock Reservation
- **Severity**: HIGH | **Category**: Data Integrity
- **File**: `app/Observers/StockReservationObserver.php:57-61`
- **Problem**: Stock reservation uses `DB::table('products')->where('id', $productId)->increment('hesabfa_reserved_stock', $quantity)` without checking if the product has sufficient sellable stock before reserving.
- **Why it matters**: Two concurrent orders for the same product can both reserve stock, leading to overselling. `hesabfa_reserved_stock` can exceed `hesabfa_physical_stock`.
- **Fix**: Add a check: `->whereRaw('hesabfa_physical_stock - hesabfa_reserved_stock - hesabfa_manual_reserved >= ?', [$quantity])` or use `DB::transaction()` with `lockForUpdate()` and validate stock before reserving.

### H7. Order Number Collision Under High Traffic
- **Severity**: HIGH | **Category**: Data Integrity
- **File**: `app/Http/Controllers/Api/OrderSubmitController.php:102`
- **Problem**: `$orderNumber = 'ZT-'.now()->format('YmdHis');` generates order numbers with second-level precision. Two orders in the same second will have the same order number.
- **Why it matters**: Duplicate order numbers break accounting, Hesabfa sync, and customer communication.
- **Fix**: Use UUID or add a random suffix: `'ZT-'.now()->format('YmdHis').'-'.Str::random(4)` or use a database sequence.

### H8. LandingController Has No Caching and Loads All Products
- **Severity**: HIGH | **Category**: Performance
- **File**: `app/Http/Controllers/LandingController.php` (entire controller)
- **Problem**: `getProducts()` loads ALL products with images on every request without any caching. This is a server-rendered Blade page.
- **Why it matters**: Every page load triggers a full product query. Under traffic, this will exhaust database connections.
- **Fix**: Add `Cache::remember()` or `Cache::flexible()`. Better: use route-level response caching.

### H9. env() Used Directly in Controller (Not Config)
- **Severity**: HIGH | **Category**: Production Breaker
- **File**: `app/Http/Controllers/Api/PaymentController.php:151`
- **Problem**: `$frontendUrl = env('FRONTEND_URL', 'http://localhost:3000');` uses `env()` outside of a config file.
- **Why it matters**: After running `php artisan config:cache`, `env()` returns `null` for all values. The frontend URL will be `null`, breaking all payment redirects.
- **Fix**: Create `config/app.php` entry or use existing config: `config('app.frontend_url')`. Move to a config file.

### H10. Duplicated Constants and Methods Across Controllers
- **Severity**: HIGH | **Category**: Maintainability
- **Files**: `OrderSubmitController.php:15-16` and `PaymentController.php:20-21` (INSTALLMENT_GATEWAYS, INSTALLMENT_FEE_PERCENT); `OtpController.php:188-201` and `ProfileController.php:209-222` (normalizeMobile); `ProductController.php:51-89` and `WishlistController.php:107-128` (formatProduct)
- **Problem**: Critical business logic (installment fee calculation, phone normalization, product formatting) is duplicated across controllers.
- **Why it matters**: When installment fee changes from 4% to 5%, you must update it in two places. If you miss one, you have inconsistent pricing. Phone normalization bugs will be fixed in one place but not the other.
- **Fix**: Extract to shared services: `InstallmentService`, `PhoneHelper`, `ProductResource` (API Resource).

### H11. Broadcast Events Synchronize (ShouldBroadcastNow)
- **Severity**: HIGH | **Category**: Performance
- **File**: `app/Events/PriceBoardUpdated.php`, `app/Events/ProductsUpdated.php`
- **Problem**: Both events implement `ShouldBroadcastNow`, meaning they broadcast synchronously during the request lifecycle instead of being queued.
- **Why it matters**: Every price sync (every minute) blocks the request while broadcasting to all connected WebSocket clients. Under load, this degrades response times.
- **Fix**: Use `ShouldBroadcast` (queued) instead, or dispatch to a dedicated queue.

## MEDIUM Issues

### M1. No Eloquent API Resources
- **Severity**: MEDIUM | **Category**: Architecture / Maintainability
- **Problem**: All API responses are manually formatted arrays in controllers. ProductController and WishlistController have different `formatProduct()` implementations (WishlistController's is missing tax calculation, responsive images, metal type fields).
- **Fix**: Create `ProductResource`, `OrderResource`, etc. for consistent API responses.

### M2. UserAddressPolicy Defined But Unused
- **Severity**: MEDIUM | **Category**: Architecture
- **File**: `app/Policies/UserAddressPolicy.php` exists, but `app/Http/Controllers/Api/AddressController.php` uses manual `$request->user()->id !== $address->user_id` checks.
- **Fix**: Use `$this->authorize('view', $address)` or `$request->user()->can('view', $address)` instead.

### M3. No Pagination on Product Listing
- **Severity**: MEDIUM | **Category**: Performance / Scalability
- **File**: `app/Http/Controllers/Api/ProductController.php:92-136`
- **Problem**: `/api/products` returns ALL products when no slugs/SKUs filter is provided. Cache key is `api:products:all`.
- **Why it matters**: As product count grows (hundreds to thousands), response size and memory usage grow linearly.
- **Fix**: Add cursor or offset pagination. Return paginated results even within the cache.

### M4. No Pagination on Order Listing
- **Severity**: MEDIUM | **Category**: Performance
- **File**: `app/Http/Controllers/Api/OrderSubmitController.php:18-28`
- **Problem**: `$orders = Order::with([...])->get()` loads ALL user orders with eager-loaded relations.
- **Fix**: Add `->latest()->paginate(20)`.

### M5. Session Lifetime Configured for 30 Days
- **Severity**: MEDIUM | **Category**: Security
- **File**: `.env.example` - `SESSION_LIFETIME=43200` (30 days)
- **Problem**: If deployed with this default, sessions persist for a month.
- **Fix**: Set to 120 (2 hours) or less for an e-commerce application. Session cookie should also have `secure: true` and `same_site: strict` in production.

### M6. CORS Allows Wildcard Paths
- **Severity**: MEDIUM | **Category**: Security
- **File**: `config/cors.php:4`
- **Problem**: `'paths' => ['api/*', ..., '*']` - the `*` allows CORS on ALL routes including the admin panel.
- **Fix**: Remove `'*'` from paths. Only allow `api/*` and specific web routes that need CORS.

### M7. Order Total Calculated Client-Side, Not Server-Validated
- **Severity**: MEDIUM | **Category**: Security / Business Logic
- **File**: `app/Http/Controllers/Api/OrderSubmitController.php:74-99`
- **Problem**: The order total is calculated from `$product->price * $item['quantity]` where `$product->price` comes from the database (good), but the `shipping_cost` is user-provided and trusted. Also, for dynamic-priced products, `$product->price` may not reflect the current price board price.
- **Fix**: Recalculate price from price board for dynamic products. Validate shipping cost against ShippingRate calculation.

### M8. Installment Fee Calculated Differently in Three Places
- **Severity**: MEDIUM | **Category**: Business Logic / Consistency
- **Files**: `OrderSubmitController.php:98`, `PaymentController.php:44`, `HesabfaObserver.php:219`
- **Problem**: Three separate implementations of 4% installment fee calculation. `HesabfaObserver` also adds 10% tax on commission, which the other two don't.
- **Fix**: Single source of truth in a service class.

### M9. No Input Validation on Hesabfa Webhook Payload
- **Severity**: MEDIUM | **Category**: Security
- **File**: `app/Http/Controllers/Api/HesabfaWebhookController.php:62-88`
- **Problem**: `$data['Quantity']` is cast to `(int)` but the webhook could send negative quantities, extremely large numbers, or manipulate stock below zero.
- **Fix**: Validate quantity is non-negative. Validate itemCode exists before processing.

### M10. Product `calculatePrice()` Iterates All Cached Products
- **Severity**: MEDIUM | **Category**: Performance
- **File**: `Modules/Product/app/Models/Product.php:109-118`
- **Problem**: `foreach ($products as $item)` iterates through all cached price board products to find a match by name. For a single product, this is O(n).
- **Fix**: Index the price board by name at cache time, or use `collect($products)->firstWhere('name', $this->price_board_item)`.

### M11. StockSyncService Updates Products One by One in Loop
- **Severity**: MEDIUM | **Category**: Performance
- **File**: `app/Services/StockSyncService.php:35-63`
- **Problem**: `syncAllStock()` iterates all quantities and calls `$product->update()` one at a time. For hundreds of products, this is hundreds of queries.
- **Fix**: Use `Product::upsert()` or chunk the updates in batches.

### M12. CancelUnpaidOrders Bypasses Model Events
- **Severity**: MEDIUM | **Category**: Business Logic
- **File**: `app/Console/Commands/CancelUnpaidOrders.php:16-25`
- **Problem**: Uses `Order::where(...)->update(...)` which bypasses Eloquent model events. StockReservationObserver's `deleted` or `updated` event will NOT fire, so reserved stock will not be released.
- **Fix**: Query each order individually and call `$order->update(['status' => 'cancelled'])` to trigger observers, or manually release stock.

### M13. No Authorization on Order Creation Endpoint
- **Severity**: MEDIUM | **Category**: Security
- **File**: `routes/api.php:59` - `POST /api/orders` has no `auth.token` middleware
- **Problem**: Anyone (even unauthenticated) can create orders. `$request->user()?->id` will be null, creating orders with no user.
- **Fix**: Add `auth.token` middleware to the order creation route.

### M14. Product Show Endpoint IDOR
- **Severity**: MEDIUM | **Category**: Security
- **File**: `app/Http/Controllers/Api/ProductController.php:143`
- **Problem**: `->orWhere("id", $slugOrId)` allows querying by ID. If IDs are sequential, an attacker can enumerate all products. This is a public endpoint so it's lower risk, but combined with the lack of pagination it allows full product enumeration.
- **Fix**: Use route model binding with scoped queries instead.

### M15. Webhook Logs Written with file_put_contents
- **Severity**: MEDIUM | **Category**: Maintainability / Performance
- **File**: `app/Http/Controllers/Api/HesabfaWebhookController.php:90-107`
- **Problem**: Uses `file_put_contents()` for logging instead of Laravel's logging system. Log cleanup runs on every webhook request (checking all log files).
- **Fix**: Use `Log::channel('hesabfa-webhook')->info(...)` with daily rotation. Move cleanup to a scheduled command.

### L2. Mixed Persian/English in Codebase

- **Problem**: Error messages are in Persian, but code comments, variable names, and some logs are in English. Config keys are English. This is fine for an Iranian app but makes onboarding international developers harder.

### L3. Missing Factories for Core Models
- **Severity**: LOW | **Category**: Testing

- **Severity**: LOW | **Category**: Business Logic

## Architecture Score Assessment

### 1. Architecture: 6/10
**Strengths**: Modular structure with nwidart/laravel-modules. Clean separation of Product, Order, Payment, Blog modules. Services layer for external API integrations. Observer pattern for Hesabfa sync.
**Weaknesses**: Duplicated business logic across controllers (formatProduct, normalizeMobile, installment constants). No API Resources. Policy defined but unused. Mixed concerns in controllers (validation, business logic, response formatting all in one method).

### 2. Laravel Best Practices: 5/10
**Strengths**: Uses Form Requests for auth flows. Rate limiters defined. Scheduled commands. Observer pattern. Proper use of `config()` in most places.
**Weaknesses**: `env()` used in controller. No API Resources. Manual array responses. `DB::raw()` with user input. No `dispatchAfterCommit`. Events broadcast synchronously. No queued jobs for heavy operations (Hesabfa sync runs in observer during request).

### 3. Performance: 5/10
**Strengths**: Product listing cached for 300s. Setting model cached forever with auto-invalidation. Price board cached with fallback. Responsive images generated.
**Weaknesses**: No pagination on products/orders. LandingController uncached. Broadcast events synchronous. StockSyncService updates one-by-one. Price calculation iterates all cached products. No `Cache::flexible()` for high-traffic data.

### 4. Security: 3/10
**Strengths**: OTP-based auth (no passwords). Rate limiting on OTP/Shahkar. CSRF excluded for API routes. Role-based Filament access.
**Weaknesses**: SQL injection. Plaintext API tokens. No token expiry/invalidation on logout. .env write from admin. SSL verification disabled. CORS wildcard. No rate limiting on order creation. Mass assignment risk. Webhook authentication optional. No HTTPS enforcement.

### 5. Maintainability: 5/10
**Strengths**: Clean model structure. Consistent naming. Modular architecture. Observer pattern.
**Weaknesses**: Duplicated code across 3+ locations. No API Resources. Mixed Persian/English. Policy unused. No tests to prevent regressions.

### 6. Production Readiness: 3/10
**Strengths**: Health check endpoint (`/up`). Scheduled commands with `withoutOverlapping`. Payment logging channel. Environment-based configuration.
**Weaknesses**: No tests. SQL injection. Plaintext tokens. No HTTPS enforcement. No queue for heavy operations. Config cache would break payment redirects. No monitoring/alerting setup. No graceful error handling for external service failures.

### 7. Technical Debt: 7/10 (high debt)
**Key debt items**: Duplicated business logic (3+ places for installment fee, phone normalization, product formatting). Unused policy. LandingController with no route. Manual array responses everywhere. No API Resources. Observer doing synchronous HTTP calls during request lifecycle.

## Self-Review: Challenging My Own Findings

### False Positives Removed
1. ~~LandingController uncached~~ - I marked this HIGH but the controller appears to be dead code (only a redirect in web.php). Downgraded to LOW. However, if it IS used via Blade views, it's a real performance issue.
2. ~~Broadcast events synchronous~~ - For a price board with ~10-50 concurrent WebSocket clients, synchronous broadcasting is acceptable. Downgraded from HIGH to MEDIUM. Only becomes a real problem at scale.
3. ~~StockSyncService one-by-one updates~~ - For a product catalog of <1000 items, this is fine. Only becomes a problem at >5000 products. Kept as MEDIUM.

### Additional Issues Found on Review
1. **Missing `auth.token` on `POST /api/orders`** (route line 59) - I initially missed this. This allows unauthenticated order creation, which is a CRITICAL auth bypass for a financial operation. Moved to HIGH (would be CRITICAL if orders contain PII).
2. **Product price not server-validated during order** - The `$product->price` is read from DB (good), but for dynamic products the price may have changed since the user viewed the product page. The order total could be stale. This is a MEDIUM business logic issue.
3. **HesabfaObserver makes synchronous HTTP calls during request** - When an order status changes to 'confirmed', the observer makes 3-5 HTTP calls to Hesabfa (find contact, save contact, save invoice, save warehouse receipt). This can take 15+ seconds and will timeout under load. This should be a queued job. **This is actually a HIGH performance issue I under-ranked.**

### Architectural Challenge
The modular architecture (nwidart/laravel-modules) adds complexity for a project of this size. With only 4 modules (Product, Order, Payment, Blog), the overhead of module-specific routes, migrations, and service providers may not be justified. A simpler flat structure with domain-based grouping (e.g., `app/Domain/Order/`) would be more maintainable. However, this is an architectural preference, not a bug - I'll keep it as a note rather than an issue.

### Scalability Concern I Initially Missed
At 100K+ users, the `users.api_token` column with a plain B-tree index will become a bottleneck for every authenticated request. Hashing tokens (C3 fix) would require a separate indexed `api_token_hash` column. The `Cache::rememberForever` on Settings will be fine since settings change rarely, but the price board cache with 120s TTL will cause all 100K users to see stale prices for up to 2 minutes after a price change. Consider WebSocket-only price updates with no HTTP fallback cache.

## Recommendations Summary
