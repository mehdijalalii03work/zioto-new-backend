## Authorization

The Pulse dashboard is protected by the `Authorize` middleware, which calls `Gate::authorize('viewPulse')`.

**Override in `AppServiceProvider.php`:**

```php
$this->app->booted(function () {
    Gate::define('viewPulse', function (User $user) {
        return $user->hasRole(['admin', 'manager', 'operator']);
    });
});
```

**How it works:**
- The gate runs inside a `booted` callback to ensure it executes after Pulse's own service provider has registered its default gate.
- It uses `spatie/laravel-permission`'s `hasRole()` method, which is the same authorization mechanism used by `User::canAccessPanel()` for Filament admin access.
- Users without an authenticated session or without one of the required roles receive a 403 Forbidden response.
- No additional authentication middleware is needed in the Pulse route middleware config because the `Authorize` middleware delegates to Laravel's `Gate`, which handles authentication checks automatically.

**Authorization flow:**
1. Request hits `/pulse` route
2. `web` middleware group runs (session, cookies, CSRF)
3. `Laravel\Pulse\Http\Middleware\Authorize` runs
4. `Authorize` calls `Gate::authorize('viewPulse')`
5. Gate resolves the authenticated user
6. Gate executes the `viewPulse` closure
7. If user has `admin`, `manager`, or `operator` role → access granted
8. Otherwise → 403 Forbidden

## Production Configuration

### Scheduler

The `pulse:check` command is registered in `routes/console.php`:

```php
Schedule::command('pulse:check')
    ->everyMinute()
    ->withoutOverlapping(5);
```

This command aggregates `pulse_entries` into `pulse_aggregates` and prunes old data. The `withoutOverlapping(5)` prevents concurrent runs and automatically releases the lock after 5 minutes if the previous run stalled.

This must be running in production. Add to your crontab:

```
* * * * * cd /path/to/project && php artisan schedule:run >> /dev/null 2>&1
```

### Daemon Requirements

No dedicated daemon is required. Pulse uses the existing scheduler (`schedule:run` via cron) for the `pulse:check` command, and ingests data synchronously during request/queue lifecycles via the `storage` ingest driver.

If using high-traffic production, you may optionally switch to the `redis` ingest driver and run `pulse:work` as a daemon with Supervisor:

```
[program:pulse-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /path/to/project/artisan pulse:work
autostart=true
autorestart=true
user=forge
numprocs=1
redirect_stderr=true
stdout_logfile=/path/to/project/storage/logs/pulse-worker.log
```

This is not required at current scale.

### Pruning

Pruning is handled automatically by `pulse:check`:
- **Entries table**: trimmed after 7 days (`PULSE_STORAGE_KEEP`)
- **Ingest data**: trimmed after 7 days (`PULSE_INGEST_KEEP`)
- A lottery-based trim check runs roughly every 1 in 1000 ingest operations

To manually clear all data:
```bash
php artisan pulse:clear
```

### Cache Serialization Resolution

Pulse caches aggregated query results (Collections) via the `remember()` method in `RemembersQueries` trait. By default, it uses the application's cache driver (`database`).

Laravel 13 introduced a security hardening in `config/cache.php`:

```php
'serializable_classes' => false,
```

This prevents any PHP class unserialization from the `database` or `file` cache stores, as they pass `allowed_classes => false` to `unserialize()`. When Pulse stores a `Collection` object in the database cache, attempting to retrieve it creates an `__PHP_Incomplete_Class` instead.

**Root cause identified via** `vendor/laravel/framework/src/Illuminate/Cache/DatabaseStore.php:593-598`:

```php
if ($this->serializableClasses !== null) {
    return unserialize($value, ['allowed_classes' => $this->serializableClasses]);
}
```

Since `serializable_classes` is `false` (not `null`), the condition is `true`, and `allowed_classes => false` blocks all class unserialization.

**Fix:** Set `PULSE_CACHE_DRIVER=array` in `.env`. Pulse query results are ephemeral (5-second TTL within Livewire polling requests), so the `array` driver is sufficient and avoids serialization entirely.

### Design Decisions

1. **Kept all recorders enabled**: For an e-commerce application that relies on queues, external API calls (Hesabfa, Tapsi, Shahkar, payment gateways), and database performance, all Pulse recorders provide actionable insights. Each has sensible defaults (1000ms thresholds) that won't generate excessive noise.

2. **Storage ingest driver (no Redis)**: The application does not currently use Redis for caching or sessions (database driver is used). Adding Redis solely for Pulse ingest would increase infrastructure complexity. The `storage` driver is sufficient at current scale.

3. **7-day retention**: Balances debugging capability with storage efficiency. E-commerce order cycles rarely require monitoring data older than 7 days.

4. **Reused existing roles**: The same `admin`/`manager`/`operator` roles used for Filament panel access control Pulse dashboard access, maintaining a consistent authorization boundary.

5. **`booted` callback for gate**: Ensures the gate override runs after Pulse's own service provider has registered its default local-only gate, preventing the local-only default from persisting.
